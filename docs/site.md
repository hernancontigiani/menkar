# The public site — how it is built, captured and checked, and why

The site is `site/`: Astro Starlight, English at `/` and Spanish at `/es/`, every image a capture of
the real app in both languages and both themes, the orchestration mode as its headline (decision
1.189). It will live at **`https://hernancontigiani.github.io/menkar/`** and is **not published
until the first release**. How its text is written — who reads it, the words, the twins, the
captures' alt text — is **`site/AGENTS.md`**, the tone guide, loaded by itself for whoever edits a
page; this file does not repeat it. The commands are in `README.md` ("Development").

## Decided (the human, 2026-11-19, topic 73; vocabulary 2026-11-20, topics 77 and 78)

| | Decision | Why |
|---|---|---|
| D1 | Spanish pages get their own captures, taken in Spanish | The locale is a parameter of the seed and the walk; its cost is twice the images and their review, not code |
| D2 | GitHub's address, `<owner>.github.io/menkar` | Free, HTTPS, no DNS to keep. Moving to a custom domain later loses the links already shared: Pages cannot redirect but with a page per URL |
| D3 | One "What comes next" page, listing only what `plans/00-STATUS.md` records as decided and user-visible, no dates, no plan numbers, reviewed at each release | Without it the main feature looks finished; a mirror of the internal roadmap promises more than is decided |
| D4 | Captures are committed under `site/src/assets/captures/` | Every image is seen before it goes live, and the build needs no Electron. Git LFS: quotas on the free plan and one more tool. Generated in the deploy: live unseen |
| D5 | A terminal in a capture shows a scripted screen per session, in the locale | Deterministic and offline. The real Claude Code needs network, an account and cost, and differs every run; a cropped terminal loses what sells the mode |
| D6 | The sidebar starts with Get started, then the orchestration mode | The human's pick over the recommended order; the mode stays the headline on the splash, whose first button is Install |
| Words | What waits on the human is an **item** / **pendiente**, its section "Awaiting you" / "Pendientes tuyos"; "topic" never appears on the site | The site follows the app's catalog and decision 1.146 (topic 78, which corrects topic 77's pick of topic/tema); the rest of the table as proposed in topic 77 |

## Its own package

`site/package.json` has its own dependencies and lockfile, and `site/.npmrc` sets
`engine-strict=true`. The app's install, `npm run ci` and the `.deb` never pull Astro, and a session
that only touches the app never installs the site. The root scripts `site:*` delegate with `npm
--prefix site`. Every script in `site/package.json` sets `ASTRO_TELEMETRY_DISABLED=1` itself, so no
way of running Astro sends its telemetry; the workflow sets it too.

Astro needs a newer Node 22 than the app: `site/package.json`'s `engines` holds its minimum, and
with `engine-strict` an install on an older Node stops at once (`EBADENGINE`) instead of leaving a
tree that cannot build.

## Pages

- **Plain Markdown, not MDX**, so the `.md` an agent copies is the page itself, with no imports or
  components in it.
- **One Markdown plugin** (`site/src/remark/menkar.mjs`) gives the pages three extensions, for the
  HTML and the `.md` alike: `![](shot:<slug>)` (a capture), `:ui[<i18n key>]` (an app label, bold,
  from the app's own catalogs, so a renamed label changes the docs with it) and `::shortcuts` (the
  keyboard page's tables, from `SHORTCUTS`, so they cannot drift from the keys). An unknown slug or
  key fails the build. **Astro 7's Markdown processor is Sätteri, not remark**: the plugin is a
  Sätteri mdast plugin registered ahead of Starlight's, whose directive restoration turns any
  directive left unclaimed back into text. `markdown.remarkPlugins` would never run.
- **A shot in HTML is two images**, the page locale's light and dark capture, each wrapped in
  Starlight's `dark:sl-hidden` / `light:sl-hidden`, optimised by Astro's image pipeline. In the
  `.md` it is one image, the light one, at its absolute URL.
- **A label with a placeholder** (`Tasks · {n}`) cannot be `:ui[…]`: the plugin prints the catalog's
  text as is. The pages name such a thing in prose.
- **The sidebar is one folder per group, autogenerated**, so a page joins it by being written in
  its folder; order within a group is each page's `sidebar.order`, the same in both twins. An
  explicit sidebar entry fails the build while its page does not exist.
- **Links are absolute with the base** (`/menkar/…`, `/menkar/es/…`), and the links validator
  checks every one, the splash's buttons included.

## The Copy page menu and `llms.txt`

Every page but the splash has a menu of our own (`site/src/components/PageTitle.astro`, overriding
Starlight's title): Copy page (fetches the page's own `.md` and copies it), View as Markdown,
`llms.txt`, Open in Claude (copies a prompt naming the page's `.md` and opens claude.ai, which is
reported not to prefill from the URL) and Open in ChatGPT (a `?q=` link). It is a `<details>`, so
it opens without script. Each page's `.md` is built by `site/src/pages/[...slug].md.ts` through the
same plugin. `llms.txt` comes from `starlight-llms-txt`, English only (the plugin reads the default
locale); its `llms-full.txt` carries both images of a shot.

## No tracking

`site/scripts/check.mjs` scans the built HTML, CSS and JS: anything loaded from another origin
fails (`src`, `srcset`, `poster`, `<link href>`, CSS `url()` and `@import`, frames and objects, a
form's action), and so does a beacon anywhere or a `fetch`, XHR, WebSocket or worker with an
absolute URL. Plain `<a href>` links out pass; the site's own origin passes. A request whose URL is
built at run time cannot be read by a scan.

## Captures

`npm run captures` builds the app, runs `playwright.captures.config.ts` under `xvfb-run` (one launch
per locale × theme, in parallel) and imports the images. Raw images go to `/tmp/menkar-captures/`,
never into the tree or `$MENKAR_FILES`. Measured on 2026-11-20: about 105 s for the whole run, and
the committed images weigh about 5 MB.

- **One registry** (`e2e/captures/registry.ts`): every capture's slug, its scene and its locales
  and themes. The site resolves `shot:` slugs and alt text from it; there is no second list. Each
  scene's walk is typed against it (`e2e/captures/scenes.ts`), so a scene without a walk is a
  compile error.
- **The seed writes the app's storage through the app's own writers** (`e2e/captures/seed.ts`) to
  explicit paths under the throwaway root, never through `saveTasks()` and its kin, whose path comes
  from the calling process's environment and would be the developer's own config. A format change in
  the app is then a compile error or the same output, never a drifted hand-written copy. What only an
  agent writes (a transcript) is a fixture: the app has no writer for it.
- **The seed's text is in `e2e/captures/strings/<locale>.ts`**, not in the app's catalogs (they ship
  in the app, and the i18n check flags unused keys). Spanish is typed complete, so a missing string
  is a compile error; a test seeds both locales and compares them with every string replaced by its
  key. Names are chosen to **sort the same in both languages**, since the app sorts sessions and
  projects by name.
- **Time is the seed's**: every timestamp derives from the `now` it is given. Today's events are
  squeezed in order after midnight when the day is young, so "Done today" holds whenever it runs;
  near midnight the run waits rather than straddle it.
- **The stand-in agent** (`e2e/captures/stand-in-claude.mjs`) prints its session's scripted screen
  and sets the terminal title the way the app reads Claude Code's state. Claude Code's own chrome
  (its permission card, "esc to interrupt") stays English in both locales, as the real CLI shows it
  and as the state reading matches it; only the conversation is in the locale. It hides the cursor,
  as Claude Code does. For a chat tab it speaks the stream-json protocol.
- **The walk proves the screen before each shot**: a ready locator plus the seed's own numbers,
  then one condition held before and after the shot — no spinner, fonts loaded, every running
  session's context ring drawn and its dot at its seeded state, nothing focused, no toast, no
  terminal scrollbar shown or fading — or the shot is taken again. No `networkidle` and no fixed
  sleep. `CAPTURE_CHECK=1` walks everything and writes nothing; `CAPTURE_ONLY` filters what is
  written, never what is walked, since screens are stateful; any page error fails the run.
- **Traps the walk works around**, each found by running twice and diffing:
  - Xvfb leaves the pointer over the terminal, which keeps xterm's scrollbar shown: the pointer rests
    on the header first.
  - Playwright's clipped screenshot shows a terminal's scrollbar for good: a part of a window is
    taken with Electron's `capturePage`.
  - A row can be drawn from a state sent before its terminal started, without its context ring; the
    walk brings a fresh state.
  - "Away since HH:MM" is main's clock: that scene shifts main's clock and runs last.
  - A click on a project row's middle can hit its rename button; a double-click on a file sometimes
    opens nothing and is tried again.
- **The importer** (`site/scripts/import-captures.mjs`) reduces each image to a 256-colour palette
  and **keeps the committed file when the new capture is the same picture**, so git grows only on
  real changes. The same picture is not equal pixels: glyph antialiasing moves between two runs of
  one screen, and a palette re-picked from a translucent screen moves much of it, while a changed
  word moves far more. So the new capture is drawn in the committed file's own palette and compared
  under two bounds, and a near tie between palette colours takes the committed file's colour; the
  bounds and the tie are in `site/scripts/same-picture.ts`, and `tests/site/captures.test.ts` holds
  them against measured cases. Two captures of one run showing the same picture fail (a navigation
  that did not happen photographs the previous screen again), unless the registry says they may; so
  does a flat image. A contact sheet per locale × theme is written for the human.
- **Every changed image is looked at.** The session that ran the capture opens each one, then signs
  it off with `npm run captures:reviewed -- <slug>…` (or `--all-changed`), which writes its hash to
  `site/src/assets/captures/reviewed.json`. `npm run ci` fails on any committed image whose hash is
  not the signed one. It cannot prove anyone looked; it proves each change was signed off by name.

## Checks

- **In `npm run ci`, no site install needed** (`tests/site/`): twins and their parity, the locale
  lists of the registry, `astro.config.mjs` and the app's catalogs agreeing, every `shot:` slug in
  the registry with its files and alt text and no file outside it, signed-off hashes, `:ui` keys,
  headings, the seed, the plugin, the scan's cases, `site/CLAUDE.md`. The twins' rules are one module
  (`site/scripts/twins.mjs`) read by both checks, so the build enforces what the tone guide says.
- **`npm run site:check`** (needs `npm run site:install`): the build with the links validator, then
  the scan, every image resolved, and the twins. **`-- --release`** also fails a page that still
  holds a `<!-- plan N: … -->` block another piece of work has to fill (the Install page's package
  repository commands until the first release fills them).
- **The site's TypeScript is in no gate**: `tsc -p site` is run by hand.

## Deploy

`.github/workflows/docs.yml` builds with `npm --prefix site run check -- --release` and deploys
`site/dist` to Pages. It runs **only by hand** until the first release, like every workflow; the
repository is public, so a run deploys. **The first deploy is the human's, at the first release**
(Settings › Pages, source GitHub Actions, then run `docs` by hand); until then the site is
previewed locally. Turning on a trigger then is the release pipeline's step. The Install page links
releases only through `releases/latest`, so a release never needs a site change; its package
repository commands come from `docs/packaging.md`.

## Rejected

- **Mintlify**: telemetry on by default and every visit through its servers, export and
  self-hosting only on its Enterprise plan. **MkDocs Material** (decision 1.189).
- **`starlight-page-actions`** for the menu: its `.md` is the raw source, so `shot:` and `:ui[…]`
  would reach the reader unrendered, and it adds share links. **`starlight-llm-actions`**: no
  locales, and it takes over the title itself. Ours is about a hundred lines with no dependency.
- **A Content-Security-Policy `<meta>`**: Starlight's inline theme script would need a hash kept in
  step with every release of it, and the scan catches the same at build time (deferred,
  `docs/NOT_BUILT_YET.md`).
- **The tone guide as a path-scoped `.claude/rules/` file**: only Claude Code loads it. A nested
  `site/AGENTS.md` with `site/CLAUDE.md` = `@AGENTS.md` loads for every agent; it is mirrored by the
  history check, since its rules change with every editorial comment.
- **Captures inside `npm run ui-check`**: specs assert behaviour, captures sell; a copy change would
  fail the suite and a test refactor would move the docs' images.
- **Captures generated in the deploy workflow**: live unseen, and Electron under Xvfb on every run.
- **The seed writing the app's JSON by hand**, as the e2e fixtures do: a second, undocumented copy
  of the app's formats that drifts.
- **Masking volatile content with CSS**: the seed owns time instead.
- **Generating the orchestration pages from the app's guide** (`plugin/guide/orchestration-mode.md`):
  the guide is written for agents too, with tool names; the site needs captures and a selling order.
  The guide stays, for agents and offline.
